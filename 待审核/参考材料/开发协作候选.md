可保留的思路是：先了解当前任务相关实现和明确要求，在有效授权内完成工作；遇到新的业务歧义或实质扩大范围时说明影响。代码应让维护者能读懂，不为局部任务顺带重构无关部分。

固定文件数、行数、模块数不适合作为所有项目的统一审批门槛。沟通频率、逐步确认和展示方式属于使用方设置，不在本候选稿中规定。

<a id="workspace-protection"></a>
## 第 3 项：工作区与 Git 保护

状态：**待后续处理，尚未采纳。** 以[第3项问题记录](../../待后续处理/03-工作区与Git保护.md)为准，以下仅供对照：

- 修改前了解相关工作区状态，分清已有改动与本次新增改动。
- 保留任务之外的修改，避免覆盖其他人的工作。
- 删除、恢复、清理等操作结合目标路径、引用关系和数据价值判断，不单凭文件名认定可丢弃。
- Git 操作按实际影响和有效授权区分；查看状态、修改本地历史和更新远程仓库不是同一类动作。
- 需要回退时明确回退对象及范围，不把整个工作区作为默认清理目标。
- 交付时说清文件修改、提交和远程更新的实际状态，不能混为一谈。

尚未确定统一条款和授权尺度，不保留原材料的命令黑名单或固定提交流程。

<a id="json-contract"></a>
## 第 9 项：JSON 空集合与空值语义

状态：待审核，尚未采纳。适用于提供 JSON 接口的项目，候选约定如下：

- 契约规定应返回的集合字段，明确“没有元素”时用 `[]` 表示；不把“未知、未加载、不适用”等不同语义直接当作空集合。
- 无记录时保留约定的分页对象和元数据，不把整个对象替换成数组。
- 标量和普通对象的空值按各自契约定义，不统一替换为 `[]`。
- 该约定只处理原本应公开的字段，不增加响应字段或放宽可见范围。
- 请求中的未传、`null` 和 `[]` 可能分别表示保留、清空或替换，需由具体接口约定，不能套用响应规则。
- 修改时核对实际 JSON；既有接口的兼容性和局部实现范围需单独评估，不为单个接口统一改动全部序列化配置。

仍需决定：是否采纳默认空数组规则、适用前提以及历史接口如何处理。

<a id="page-api-map"></a>
## 第 10 项：页面操作与接口对应

状态：待审核，尚未采纳。适用于需要界面与接口协作的项目。

可按实际协作需要记录“页面或操作 → 调用时机 → 接口 → 关键字段与状态”。从页面需求核对缺口，也从接口核对用途，避免只整理已有接口就认定需求完整。

重点区分展示字段、提交参数、组合文案和固定内容；标出已经实现、待实现、暂缓及不在本期范围的部分。接口可访问、页面有原型和完整业务可用是不同状态。

文档格式、编号、截图样式及存放目录由使用方决定。是否需要独立文档、需要详细到什么程度，仍待评审，不要求每个接口制作固定格式的截图或多份交付文件。

<a id="issue-handoff"></a>
## 第 13 项：问题、复盘与交接

状态：待审核，尚未采纳。可保留的核心是让后续维护者找得到问题和处理依据：

- 说明现象、触发条件、原因与处理方式；原因未确认时保留判断边界。
- 把实际验证结果与未验证事项分开，不用推测填补结果。
- 记录影响后续工作的决定、遗留和暂停事项，给出必要的代码或文档入口。
- 同一问题优先更新已有记录，避免多份文档分别维护冲突状态。

是否补充独立条款，应先核对已有 AI 辅助开发规范的复盘与交付内容，避免重复要求。固定归档目录、逐次交互日志、提醒频率及完整报告模板不纳入本候选稿。
