# Hibernate ORM 事务与更新

2026-11-17 待审稿。适用于使用 Hibernate ORM 的 Java 项目。代码片段使用 Jakarta Persistence 接口，Spring 项目可采用下文的事务边界。实体沿用[实体映射示例](<02 实体映射与数据库结构.md>)中的 `ProductEntity`，表名为 `product`。版本号示例使用 `Long version` 和 `@Version`。[指南目录](README.md)

## 1. 先确定事务边界

- 以一次需要原子完成的业务写操作为边界。在同一事务中查找目标、检查权限和数据范围、验证业务状态、修改并完成相关数据库写入。对外部系统的调用另行确定失败及重试方式。
- 采用 Spring 声明式事务时，将边界放在由容器管理并从代理外部进入的 Service 方法上。在默认代理模式下，同一实例内部调用不会触发被调用方法上的事务设置。如果调用方已有事务，内部方法仍在调用方事务中执行。经代理调用时，默认传播行为 `REQUIRED` 加入已有事务，没有事务时才开启一个。需要独立提交时，再选择明确的事务传播行为并验证其影响。[Spring 的事务注解与代理](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html) · [Spring 事务传播](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html)
- Spring 默认对逸出事务方法的 `RuntimeException` 和 `Error` 回滚。受检异常默认不会触发该回滚规则。业务使用受检异常表示写入失败时，配置具体的 `rollbackFor`，并验证实际结果。若方法捕获异常后正常返回，明确事务是否已经标记为只能回滚，再按项目约定传播错误或标记回滚。[Spring 的回滚规则](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html)

后台入口同时执行[操作与数据范围检查](<../../10-10 通用开发规范.md#7-权限检查>)。涉及多数据源时，核对当前事务管理器与实际参与写入的持久化单元。

### 1.1 Service 显式处理关联写入

关联映射采用无级联和无自动孤儿删除的配置。Service 明确决定关联记录需要新增、更新还是删除，逐项执行权限、数据范围和业务状态检查。关联表通过对应的实体和明确的数据访问操作维护，例如用 `ProductTagEntity` 新增或移除商品标签关系。[关联实体映射](<02 实体映射与数据库结构.md#2-按查询和写入需要选择关联映射>)

- **新增。** 先确认被引用记录可用。主记录与关联一同新增时，先建立主记录并取得标识，再写依赖该标识的关联记录。
- **修改。** 读取现有关联，按业务规则确定新增、更新或移除的关联记录，再执行对应操作。
- **删除。** 先确定应清空引用、删除关联表记录还是阻止删除。需要清理关系时，先显式处理关联记录，再删除主记录。解除关联时保留仍由其他业务使用的共享数据。

同一业务操作涉及的写入在同一个事务中完成，任一步失败时整体回滚。需要数据库按特定顺序执行时，核对实际 SQL，必要时在步骤间显式 `flush()`。同步后继续使用原事务。

## 2. 管理状态、变更检测和 flush

| 操作 | 使用时核对什么 |
| --- | --- |
| 查询并修改实体 | 持久化上下文管理实体及其状态。事务中读取的受管实体需修改时，直接调用领域方法或设置允许修改的字段。Hibernate 在同步时检测变更，并为需要更新的实体生成 SQL。 |
| 实体离开持久化上下文 | 分离实体的普通赋值不会直接写库。需要更新时，通常在新事务中重新加载受管实体，再应用经过验证的输入。使用 `merge()` 时，它把传入状态复制给受管实例，应核对复制范围并使用返回实例。 |
| `flush()` | 把当前上下文中待同步的变更发送给数据库。事务仍待提交，已执行的事务内写入仍可回滚。在 `AUTO` 模式下，提交前和部分相关查询前都可能发生同步。 |

有后续步骤需要先得到约束校验或执行结果时，可以显式 `flush()`。显式同步可能同时写出上下文中的其他待处理变更。提交仍可能失败，响应成功以实际提交为准。[Hibernate 的实体更新与变更检测](https://docs.hibernate.org/orm/6.6/userguide/html_single/#pc-managed-state) · [Hibernate 的 flush 行为](https://docs.hibernate.org/orm/6.6/userguide/html_single/#flushing) · [Jakarta Persistence 的 EntityManager API](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/EntityManager.html)

## 3. 局部更新与乐观锁

写入请求用独立的输入对象，只接受本次操作允许修改的字段。需要支持局部更新时，区分未传字段与显式清空，后者还要校验字段是否可为空。业务字段修改范围与 SQL 的列数是两件事，Hibernate 可能生成包含多个可更新列的语句。如确实需要控制 SQL 更新列，再评估并验证 Hibernate 的 `@DynamicUpdate`。[Hibernate 的动态更新说明](https://docs.hibernate.org/orm/6.6/userguide/html_single/#pc-managed-state-dynamic-update)

并发更新涉及两个时间区间。

1. **用户读取旧数据到提交编辑。** 编辑界面读到的版本随写入请求返回。新事务加载当前记录，在应用更改前比较请求版本与当前版本。只加载最新记录并直接写入，会漏掉用户基于旧页面提交的情况。
2. **新事务加载记录到实际写库。** `@Version` 由持久化实现管理。实际更新时校验原版本，并更新版本值。并发导致版本不匹配时可能在同步或提交时才报错。按项目约定提示冲突，让用户重新读取和核对变更，同一事务中的其他写入也按失败处理。[Jakarta Persistence 3.2 第 3.5 节锁与并发](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html)

以下为 Service 局部更新片段，`@Transactional` 来自 Spring。`loadEditableProduct` 从当前事务加载受管实体，检查调用者能否修改该商品及相应数据范围，并处理记录不存在或不可修改的情况。`request` 表示通过输入校验的改名请求，`version` 为必填。项目中的 `VersionConflictException` 是非受检的业务冲突异常。

```java
@Transactional
public void renameProduct(Long id, ProductRenameRequest request) {
  ProductEntity product = loadEditableProduct(id);
  // 比较编辑时的版本，避免旧页面覆盖新数据。
  if (!Objects.equals(request.version(), product.getVersion())) {
    throw new VersionConflictException();
  }
  product.rename(request.name());
}
```

版本值用于比较，实体版本由持久化实现更新。若本次提交没有改变实体状态，可能没有实际的版本更新。如果业务要求连这种请求也校验事务内的并发变化，单独评估 `LockModeType.OPTIMISTIC` 等做法并用双事务测试确认。版本冲突的转换应覆盖事务提交阶段的异常。[Jakarta Persistence 的 Version 注解](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/Version.html) · [Jakarta Persistence 3.2 第 3.5 节锁与并发](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html)

## 4. JPQL 批量更新

受管实体逐条修改适用于需要逐个执行校验和其他业务动作的场景。数据量和更新规则适合直接操作一批记录时，可以用 JPQL `UPDATE`。它直接更新数据库，跳过逐实体的自动乐观锁和生命周期处理。当前持久化上下文中已加载的受影响实体不会随之更新。[Jakarta Persistence 3.2 第 4.11 节批量更新与删除](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html)

- 将允许修改的范围和业务条件写进语句。比如按受信的供应商范围改名时，`WHERE` 约束使用服务端权限判定得到的 `supplierId`，不能用调用方传入的供应商编号代替。写入前显式完成需要的校验和审计安排，检查 `executeUpdate()` 返回的受影响实体数是否符合业务预期。
- 版本策略按业务决定。对数字版本，可用 `set p.version = p.version + 1` 更新版本，让已有旧版本的编辑随后产生冲突。若要验证某条记录的预期版本，还要在 `WHERE` 中同时带上该记录的标识和预期版本，并检查返回数量。Hibernate HQL 的 `update versioned` 能更新版本，属于 Hibernate 扩展，同样不能替代业务需要的版本条件。[Hibernate 用户指南的批量变更章节](https://docs.hibernate.org/orm/6.6/userguide/html_single/)
- 优先在尚未加载受影响实体的持久化上下文中执行。若必须和其他写入共用上下文，先处理待同步改动。需要继续使用受影响实体时，按范围 `refresh()` 或 `clear()` 后重查。清空上下文前确认没有需要保留却尚未同步的改动。另开事务时同时核对它对外层操作原子性的影响。

## 5. 在目标数据库验收

用项目真实调用入口、事务配置、数据库类型与版本验证，核对提交后的数据库结果、回滚后的状态以及必要的 SQL。测试本身的事务边界要允许观察业务实际提交和回滚。

| 场景 | 验收结果 |
| --- | --- |
| 写入同步后业务失败 | 写入已经发送到数据库后触发可回滚的失败，从独立事务重新查询，确认本次计划一起提交的改动均未留下。项目使用受检异常时也覆盖该分支。 |
| 关联新增、修改和删除 | 执行各操作，核对实际 SQL 次序、关联表结果及共享记录是否保留。在关联写入后触发失败，再从独立事务核对主记录和关联记录均已回滚。 |
| 两次并发编辑 | 用两个独立事务读取同一记录，先后提交不同修改，验证后写发生冲突，先提交的值、版本和业务结果保持一致。 |
| 提交旧页面 | 两次请求之间先由其他请求更新。旧版本提交被拒绝，其他未授权字段不变。 |
| 越出数据范围 | 对越界的商品发起局部或批量更新，确认数据库值和版本均未改变。 |
| 批量更新 | 核对条件、影响数量、版本策略、事务回滚结果，以及更新后重新查询的实体状态。也验证先加载再批量更新时的上下文处理。 |
