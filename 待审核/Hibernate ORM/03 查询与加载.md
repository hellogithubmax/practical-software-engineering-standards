# Hibernate ORM 查询与加载

## 1. 从调用方需要的结果开始

| 场景 | 建议做法 |
| --- | --- |
| 页面列表、详情、导出 | 用 `Param` 接收筛选和排序，按用途投影到 `Vo`。跨层传输对象（DTO）按实际合同设计，页面展示对象沿用 `Vo` 后缀。投影只选择调用方需要且能查看的字段。 |
| 在事务内执行需要实体状态的业务 | 查询 `Entity`，关联默认保留标量 ID。所需数据按用例显式查询，再在 Service 事务内组装 `Vo` 或 DTO。 |
| 有跨表条件或排序 | 在查询中明确关联、筛选和排序。固定条件优先用清楚的 JPQL；条件组合较多时，可用 Criteria API。确需 HQL 扩展或原生 SQL 时，注明所用能力及验证过的版本和数据库。 |

`ProductEntity` 对应数据库的 `product` 表，HQL 和 JPQL 使用 `ProductEntity` 及其 Java 属性，原生 SQL 才直接使用表名和列名。对外示例沿用仓库的 `Param`、`Vo` 命名。 [Java 业务模块目录](<../../30-10 Java 通用代码规范.md#22-java-业务模块的常见目录>) · [Hibernate HQL 指南](https://docs.hibernate.org/orm/7.4/querylanguage/html_single/) · [Jakarta Persistence 3.2 第 4 章](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html)

## 2. 参数绑定和跨表投影示例

- 用 `:supplierId` 等命名参数与 `setParameter` 绑定值。动态排序从允许的字段和方向中选固定表达式，表名、字段名和语法关键字需由程序决定。`LIKE` 搜索先明确 `%` 和 `_` 是否按字面匹配，要按字面匹配时按选定的转义字符处理。用 `IN` 时明确空集合语义，例如直接返回空结果或省略可选条件；避免把两种含义混在一起。 [Jakarta Persistence 3.2 第 3.11 节与第 4.7.4 节](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html)
- 列表先定义一行代表什么，再选投影。下面一行代表一个商品，按已校验的供应商标识查商品，补供应商名称。采用标量 `ProductEntity.supplierId`，另有映射 `supplier` 表的 `SupplierEntity`（`id: Long`、`name: String`），示例不要求在商品实体上新增关联属性。`LEFT JOIN` 保留符合筛选但查不到供应商记录的商品，名称以 `null` 表达。使用显式实体连接前，核对项目实际 Jakarta Persistence/Hibernate 支持的语法。 [Hibernate HQL 指南 · Explicit root joins](https://docs.hibernate.org/orm/7.4/querylanguage/html_single/) · [Jakarta Persistence 3.2 第 4.4.5 节及第 4.9.2 节](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html)

```java
package com.example.product.vo;

/**
 * 商品列表所需的展示数据。
 *
 * @param id 商品标识
 * @param name 商品名称
 * @param supplierName 供应商名称，查不到供应商记录时为空
 */
public record ProductListVo(Long id, String name, String supplierName) {}
```

以下代码放在 Service 事务内。`em` 为 `jakarta.persistence.EntityManager`，`supplierId`、`offset`、`pageSize` 来自已校验的 `ProductQueryParam` 或相应调用参数。`offset` 从 0 开始，`pageSize` 必须为正数并按项目约定限制上限。示例展示筛选和加载，接入受保护接口时须追加适用的数据可见范围。

```java
List<ProductListVo> items = em.createQuery("""
        select new com.example.product.vo.ProductListVo(p.id, p.name, s.name)
        from ProductEntity p
        left join SupplierEntity s on s.id = p.supplierId
        where p.supplierId = :supplierId
        order by p.name, p.id
        """, ProductListVo.class)
        .setParameter("supplierId", supplierId)
        .setFirstResult(offset)
        .setMaxResults(pageSize)
        .getResultList();

long total = em.createQuery("""
        select count(p.id)
        from ProductEntity p
        where p.supplierId = :supplierId
        """, Long.class)
        .setParameter("supplierId", supplierId)
        .getSingleResult();
```

例中供应商主键至多命中一行，连接只补展示，没有改变商品集合，所以计数可省去该连接。如果增加供应商名称筛选，列表和计数都要采用等价的跨表条件。若分页条件可选，建议用同一份查询条件构造逻辑，分别生成列表和计数所需的条件。

## 3. 选择加载方式并排查 N+1

- **默认由 DAO 或 Service 显式处理关联。** 实体保留 `supplierId` 等标量关联标识。DAO 可用普通 `JOIN` 投影或按 ID 查询。需要分开读取时，Service 在事务内组织 DAO 查询，从本批结果提取并去重所需 ID，再用显式 `IN` 批量查回关联数据，按 ID 组装 `Vo`。普通 `JOIN` 投影和显式按 ID 查询由调用方决定读哪些数据，属于显式查询，不属于这里所说的级联查询。跨表筛选和排序参与原查询，仅用于展示的字段可以在分页后补读。避免在循环中逐条查询关联。 [Hibernate ORM 官方简明指南 · Association fetching](https://docs.hibernate.org/orm/7.4/introduction/html_single/#association-fetching)
- **保持查询到界面的边界。** 不使用 `jakarta.persistence.fetchgraph` 把未列明的关系隐式视为懒加载。Service 事务内完成查询与结果组装，Controller 使用已组装的返回值，模板渲染、JSON 序列化和其他结果读取都不触发 SQL。Spring Boot Web 项目设置 `spring.jpa.open-in-view=false`，按真实界面和接口验证这一边界。 [Jakarta Persistence 3.2 第 3.8.1.1 节](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html) · [Spring Boot · Open EntityManager in View](https://docs.spring.io/spring-boot/reference/data/sql.html#data.sql.jpa-and-spring-data.open-entity-manager-in-view)

### 3.1 级联查询须经人工确认

本指南将返回实体时，通过 `EAGER` 对象关联、`JOIN FETCH` 或实体图让 ORM 同时加载关联实体的做法称为级联查询。一般采用 DAO 或 Service 的显式查询。确需级联查询时，先说明具体业务入口、要加载的关联及数据量、显式方案为何不合适，以及实际 SQL、查询次数、返回行数和分页表现。经人工明确确认并记录适用范围后才采用，未确认时继续用显式方案。

对象关联限定在确认的范围内，显式声明 `FetchType.EAGER`。Hibernate 仍可能用额外的 `SELECT` 补读关联，产生 N+1。使用 `JOIN FETCH` 时要核对生成 SQL，只有对应的对象关系已映射时才可写 `join fetch p.supplier`。需要保留没有关联项的根记录时选 `LEFT JOIN FETCH`。并行连接多个集合会放大数据库结果行数，避免把筛选后的不完整集合交给业务；涉及分页时核对第 4 节所述行为。确认只覆盖相应的读操作，继续禁用懒加载和级联写入。 [Hibernate ORM User Guide · Direct fetching vs. entity queries](https://docs.hibernate.org/orm/7.4/userguide/html_single/#fetching-direct-vs-query) · [Hibernate HQL 指南 · Association fetching](https://docs.hibernate.org/orm/7.4/querylanguage/html_single/#explicit-fetch-join)

## 4. 分页、总数和集合关联

1. **按业务结果分页。** 先确定一行是商品、子项还是聚合分组。列表及总数使用相同筛选和数据可见范围。若列表以商品为单位，利用 `exists` 按子项筛选可避免一个商品变多行；若必须连接多个子项，处理列表的重复根记录，并在计数中用与列表等价的去重或分组口径。排序加唯一键作稳定的末级排序，例如 `order by p.name, p.id`。
2. **集合加载与根记录分页分开考虑。** Jakarta Persistence 3.2 对集合 fetch join 配合 `setFirstResult`、`setMaxResults` 的效果不作保证。Hibernate 7.4 为支持子查询内限制和偏移的数据库增加了 SQL 分页处理；其他方言仍可能先读取匹配行再在内存截取。核对所用 Hibernate 版本、方言及生成 SQL。 [Jakarta Persistence 3.2 第 3.11.1 节](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html) · [Hibernate HQL 指南 · Limits and offsets](https://docs.hibernate.org/orm/7.4/querylanguage/html_single/#limit-offset) · [Hibernate 7.4 迁移指南](https://docs.hibernate.org/orm/7.4/migration-guide/)
3. **可用两阶段读取集合。** 第一步以商品为单位，用完整的筛选、权限条件和稳定排序在数据库取一页商品 ID；总数也按同样的商品集合统计。第二步用本页 ID 批量查必要字段和子项，保持相同的数据隔离约束，按第一步取得的 ID 顺序重组；`IN` 的顺序不代表返回顺序。空页跳过第二步，接口承诺返回总数时仍给实际总数。分步读取和计数涉及并发变化时，按项目一致性要求选择事务及隔离级别，并明确页内记录发生变化时如何处理。 [JSON 接口规范 · 响应数组与分页](<../../60-10 JSON接口规范.md#响应数组与分页>)

## 5. 验证实际 SQL 和结果

| 核对点 | 建议证据 |
| --- | --- |
| 查询和绑定值 | 开发或测试环境查看 `org.hibernate.SQL` 的 `DEBUG` 日志。需要看绑定类型或值时，按实际 Hibernate 版本短期开启对应日志，如 7.4 的 `org.hibernate.orm.jdbc.bind` `TRACE`，使用测试数据并避免记录敏感值。 |
| SQL 条数和行数 | 在新持久化上下文中分别验证单条、多条且关联对象不同的记录。关联对象相同或缓存命中可能掩盖 N+1。用 JDBC 层语句计数或 Hibernate `Statistics` 辅助排查，分开看列表、计数和额外关联查询，核对 SQL 条数是否随记录数增长及联接是否放大行数。 |
| 分页和执行计划 | 对照返回的 ID 顺序、总数和 SQL 的实际分页位置。用具有相同排序值、多个子项及越界页的样例核对；重要查询在目标数据库用代表性数据和参数查看执行计划。总数及权限边界与列表一致。 |
| Service 返回后的使用 | 在关闭 OSIV 的实际页面和 JSON 接口中，确认 `Vo` 所需字段齐全，从读取、渲染到序列化均不发出额外 SQL。 |
